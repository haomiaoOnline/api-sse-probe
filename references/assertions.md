## 两列分别写什么

**判断依据（公共）**写这条用例实际需要的检查类型，例如：

> HTTP 200 / 文本回复 / 衍生问题

> HTTP 200 / 文本回复 / title / skillId

**特殊判断依据**写明确可复现的值条件，例如：

> title是“灵犀服务”；回复中包含“小猫”和“喂食”

> 回复中有“音量”或“声音”或“指令已下达”

> 回复中包含“湖南卫视”；skillId是“VIDEO30BFF29645B2B2E2EB6C44AE7”

不要求写 JSON/Python。不使用“围绕主题”“体现意图”“有有效业务回复”等宽泛句式；这些 v1.15 写法会在业务请求前提示迁移。

## 公共检查类型

| 类型 | 明确含义 |
| --- | --- |
| HTTP 200 | 实际 HTTP 状态必须为 200；其他预期 HTTP 状态可同样写出 |
| 文本回复 | 助手 data.text 流式拼接后有非空正文 |
| 衍生问题 | 实际 data.questions 数组至少有一个非空字符串 |
| title | 存在非空的真实业务标题；衍生问题的“你可以继续问我”不计入 |
| skillId | 在允许的实际业务字段路径中存在非空 skillId |
| SDK 或 sdk | 实际 data.sdk 非空；不是正文提到“SDK” |
| deeplink | 实际 data.deeplink 非空；空字符串不通过 |

只给用例填写需要的类型，不把全部类型加到每一行。公共列的每项与特殊列的每项都要满足。

HTTP/SSE Content-Type、合法 JSON 业务帧及必要 `[DONE]` 仍由协议层校验，不因关键词命中而豁免。

## 特殊条件写法

| 条件 | 实际检查 |
| --- | --- |
| 回复中包含“杭州”和“天气” | 助手正文两个词都出现，顺序不限，不固定全文 |
| 回复中有“音量”或“指令已下达” | 正文任一项出现即可 |
| 回复中包含“毛不易”和（“歌”或“音乐”） | 必须有歌手名，另两个词任选其一 |
| 回复中不包含“取消收藏” | 正文不得出现明确列出的词；通常与正向要求一起写 |
| title是“灵犀服务” | 实际业务标题精确等于该值 |
| title包含“外卖” | 实际业务标题包含该词，不固定宣传标语全文 |
| title包含“关爱”或“健康” | 任一业务标题满足一个允许词即可 |
| 有追问信息 | 与“衍生问题”同义，检查真实非空 questions 数组 |
| skillId是“完整ID” | 实际业务字段的 ID 精确匹配，不能只在正文提到该字符串 |
| 有skillId是“完整ID” | 与上一句相同 |
| sdk.package是“com.czly.tabletmusic” | 检查实际 SDK 包名 |
| sdk.name包含“绘本” | 检查实际 SDK 名称/页面标识 |
| deeplink以“cmcc://com.ophone.reader.ui”开头 | 检查实际业务链接的稳定前缀，不固定动态参数 |

回复条件只查助手 data.text；title 条件只查助手 data.title 或 background.title。正文提到“外卖”不能替代外卖标题，标题里有词不能替代正文词。

“有追问信息”不是搜索这几个字，也不是凭正文中一个问号通过。如果需要检查正文追问措辞，可另写 `回复中有“哪首”或“歌手”或“想听”`。

## 多个词和多个条件

同一个文本或标题条件中：

- “和”“且”“并且”“以及”“与”“、”表示全部满足。
- “或”“或者”“或是”表示任一满足。
- 支持中文/英文括号，先计算“和”，再计算“或”；复杂时建议明确加括号。
- 相邻引号词兼容旧写法并按全部满足，例如 `回复中包含“新闻联播”“CCTV1”`。
- 引号中的词不再自动展开同义词；需要哪些候选表达，就在单元格里明确列出。

不同条件用中文分号或换行隔开，表示全部满足：

> title包含“外卖”；回复中有“想吃”或“吃什么”或“想点”或“外卖”

也支持：

> title是“灵犀服务”，回复中包含“小猫”和“喂食”

引号内的逗号、分号和斜线属于值本身，不会拆开。例如 `title是“灵犀外卖，点单无忧”` 是一个标题值。

缺引号、连接词缺一边、括号不成对等受支持句式错误，在发起真实请求前报错，不静默忽略。

## skillId 和标题的边界

`skillId是“X”` 只查看助手业务 data 中的 `skillId`、`jsonHeader.skillId`、`jsonBody.skillId`、`jsonBody.params.skillId`。jsonHeader/jsonBody 可以是序列化 JSON 字符串，也可以直接是对象。

至少一条真实业务记录中出现预期 ID 才能通过。同一候选记录如果同时提供 header/body ID，已出现的 ID 必须一致且等于预期；不能让错误 body ID 被正确 header ID 掩盖。单独这句话不隐含要求固定 code，也不隐含 header/body 必须同时出现。确实要同时检查双字段或 code 时，分别写出完整字段条件或使用已支持的同帧组合规则。

原始请求、顶层 model/session/reqId、正文中的 ID 字符串、衍生问题，都不能满足 skillId 条件。

标题按业务用途设置：原表明确要求标题精确值时用“是”；业务卡片有稳定关键词而标语可能变化时用“包含”。不要因为许多样本都有通用“灵犀服务”，就给所有用例强制相同标题；也不要把样本中的错误页面标题固化为预期。

## 避免过严或过宽

保留明确的必需标识和针对性字段，文本只选稳定关键信息与合理分支，不复制完整样本回复，也不默认锁定日期、气温、价格、余额或推荐名单。

例如：

- 天气：`回复中包含“杭州”和（“天气”或“气温”或“温度”或“晴”或“雨”）`。
- 音量：`回复中有“音量”或“声音”或“指令已下达”`；只有明确列出“指令已下达”的用例才接受该分支。
- 外卖：`title包含“外卖”；回复中有“想吃”或“吃什么”或“想点”或“外卖”`。
- 直播：正文频道词与实际唯一 skillId 分别判断，不能相互替代。

这些是明确的文本/字段检查，不提供隐藏的意图容错，也不证明设备执行成功。正文包含“播放”可能是在说明“不能播放”；若用例要求执行成功，应另列明确结果条件，不能仅凭一个“成功”词推断（“没成功”同样含该词）。

## 已有规则与验收

原有 `文本回复包含“词”`、出行建议、字段前缀/等值/非空、视频双 skillId 复合句式和 JSON all/any/not/same_frame 保留。新的普通表格无需填写 JSON。

支持原九列中文 CSV：`序号,场景,类别,语料,判断依据（公共）,特殊判断依据,研发负责人,deviceId,响应结果`。公共/特殊两列独立继承“同上”。I 列只是历史样本，不作为本次真实响应参与判断。

用户限制每批最多 10 条时，先从完整 CSV 提取不超过 10 条的批次文件，再执行 `python3 scripts/probe.py --source csv --cases <批次文件>`。不能直接执行完整 165 条 CSV 做实时验收。历史 SSE 全量离线回放必须标明“回放”，不当作实时结果。真实拨测沿用已授权飞书设置；明确不通知时使用 `--no-feishu`。

失败报告保留具体缺失条件、实际字段值和完整已接收 SSE；敏感语料和原文只进入本地私有报告，不进入共享投影或团队发布包。
