# 团队通用化现状与改造路线图

目的：明确 **已经可以交付的团队 Skill** 与 **尚未完成的通用平台能力**，避免因文档完善就误认为协议、运维、权限已经通用化。

## 当前复用能力盘点

| 能力 | v1.9.0 现状 | 适用范围 |
| --- | --- | --- |
| 标准 Agent Skill 入口 | 已提供 SKILL.md、完整包和受控安装 | 可在支持磁盘 Skills 的 Agent 中识别，但产品加载路径各异 |
| 数据来源 | CSV/JSON/Tencent 电子表格只读 MCP | 同类带场景、语料、设备、断言的用例 |
| API 请求 | 固定 JSON 结构、签名头、时间戳、SSE流 | 与当前接口契约兼容的 API；不支持任意签名动态计算 |
| 断言 | 关键词 all/any、禁止词、文本回复、结构化衍生问题/出行建议 | 命中严格可验证；新语义须扩展规则 |
| 统计 | 首业务帧近似 TTFT、完整请求、PASS/FAIL/ERROR、慢首帧 | 可用于同类流式 API 性能回归 |
| 报告 | 本地 JSON v5、Markdown、失败摘录、飞书五指标+同一卡片完整失败编号（超限拒发） | 团队群可看失败摘要，完整回复仍仅本机 |
| 部署安全 | Manifest 安装、公开配置模板、私有文件隔离 | 需团队权限规范及各成员独立认证 |
| 任务执行 | 串行、同步、整批完成写报告 | **未实现**长期后台、暂停续跑、运行中进度、任务队列 |

## 技术解耦：建议的目标接口

```text
Agent CLI/Skill
    |
    +-- SourceProvider             [CSV/JSON/Tencent/未来Sheets/Feishu]
    |      -> Iterator[Case]
    |
    +-- ApiProfile                 [按服务定义URL、headers、body]
    |      +-- AuthStrategy         [固定头、HMAC、OAuth、签名插件]
    |      +-- RequestBuilder       [标准JSON/其他接口]
    |
    +-- StreamClient               [SSE/未来HTTP JSON/WebSocket]
    |      +-- ResponseExtractor    [把业务输出归一化为字段]
    |
    +-- AssertionEngine            [可插拔规则、场景期望]
    +-- ExecutionScheduler         [并发/限速、检查点、幂等恢复]
    +-- ResultStore                [SQLite/JSONL、敏感数据加密、版本]
    +-- ReportRenderer             [JSON、Markdown、可权限访问的在线报告]
    +-- NotificationAdapter        [Feishu/未来企业消息与告警]
```

本项目已经有 `SourceProvider` 的雏形、`assertion_rules.py`、`reporting.py` 和独立飞书渲染/传输层，但**没有实现上图中大部分通用接口和运行器**。不要通过更改 README 来宣称已有动态认证插件/并发/在线共享报告。

## 优先级与验收标准

### P0：团队可信分发与不误操作（本轮已做/在验收）

- [x] 盘点实际安装代码，补齐 SKILL.md 的完整可执行 Agent 路径，统一 README 的 v1.8 现行口径。
- [x] 用团队发布 manifest 避免把私人 `config.*.local.json`、`reports/`、`.env` 放入安装包；初次安装不覆盖已有目录。
- [x] 默认配置飞书关闭，必须经过群可见性审批才启用。
- [x] 将安装版独有的 `read1` SSE 分块代码补回源码，并加入离线回归。
- [ ] 每个团队成员在 Windows/macOS 上独立完成一次无密钥泄露的实际安装与读表验收（需要其机器授权，无法由此仓库保证）。
- [ ] 明确团队内版本负责人、凭据发放与轮换责任、报告留存/删除周期。

### P1：解决全量任务不可恢复及可复现性（建议下一轮）

- [ ] 将 `run_case` 结果逐条写入私有 JSONL/SQLite，写成功才标记完成；异常重启可核对并从未完成 ID 接着执行。
- [ ] 可配置并发/限速，但必须有源站承受能力和接口测试授权；默认低频执行，避免引入新的网络连接错误。
- [ ] 显式 `--case-ids`、`--limit`、`--resume <run_id>`、`--dry-run` 参数，减少按物理表格行猜 ID 的风险。
- [ ] 增加任务运行中状态、计划/已完成/错误数、总耗时预估、外部进程健康检查；支持从后台独立运行，不依赖 ChatGPT 会话。
- [ ] 增加以 `run_id + case_id` 为键的幂等机制和消息投递批次状态，避免断网时不确定的重复测试/群推送。
- [ ] 验收：模拟第73条崩溃并恢复，只重跑未完成用例；最终总数=165、报告完整、飞书不重复。

### P1：API 通用协议适配（需明确业务目标后推进）

- [ ] 统一业务 `ApiProfile` 规范：请求方法、URL、header/密钥引用、请求体模板、SSE路径、用户语料字段。
- [ ] 可扩展认证策略：固定签名、HMAC随timestamp变化、OAuth Token刷新；所有密钥来自私有配置/安全密钥管理。
- [ ] 独立 response extractor，不再把某个业务的 `choices[].delta.content.data` 假定为所有 API 的结构。
- [ ] 抽象断言规则，以每个团队项目的可插拔规则库/JSON Schema 管理；默认不让LLM“主观判定通过”。
- [ ] 以两个**不同业务协议**的真实授权测试证明可重用，而不只是换用例表。

### P2：团队协作与在线报告

- [ ] 受控存储/访问：Feishu云文档或私有Web看板中展示完整报告，按角色分配权限，敏感语料/回复按策略脱敏与加密。
- [ ] 统一报告链接、历史趋势、执行状态、慢首帧告警、按场景和责任人筛选。
- [ ] 通用通知模块可独立版本化，让日报/RSS/其他 Skills 复用，不需要复制整个拨测器。
- [ ] 版本发放、安装/升级/回滚、跨系统测试矩阵、测试环境与生产环境隔离、密钥轮换SOP。

## 决策原则

优先完成P1的**状态持久化与断点续跑**，再讨论并发与全量长期任务。过去长批次因外部运行时限而终止，单靠更长的交互命令不能彻底解决。当前团队版的目标是**同协议、安全易部署、可重现验收**；真正“不同类型 API 都可插拔”属于后续研发，需单独安排开发量与测试。

## v1.9.0 本轮原始SSE能力与后续空间

已实现失败原始SSE的**按目标最新快照覆盖**，具备全部失败帧字节级诊断；这是受限本地存储而非共享在线报告。下一阶段仍需逐条可恢复运行状态、执行断点、结果保留周期、并发互斥、团队可授权检索原始流与密钥管理。请勿将当前 `.pending` 误当作已经实现的运行断点。

## P1/P2报告云输出后续工作（接口已预留）

本轮已完成纯报告模型、Markdown纯渲染、OutputRegistry和FileOutputAdapter，以及安全的默认云共享投影。**尚未完成**飞书多维表格/云文档的SDK/API写入。未来建议先实现 FeishuBitableOutput（Run+CaseResult双表关联、run_id/case_id幂等更新、授权应用与字段映射），再实现 FeishuCloudDocOutput（目录权限、文档块/图片排版、按目标最新/按轮次历史两种策略、更新冲突与回滚）。完成前用户不能靠填写类型直接使用云输出。当前群通知是独立的消息输出，不等于报告落到云端。详见 [output-adapters.md](output-adapters.md)。
